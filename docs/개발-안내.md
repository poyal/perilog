# 개발 안내

페리로그는 Galaxy Z 플립7을 우선 대상으로 만든 개인용 복막투석 기록 앱입니다. 로그인 없이 기록을 기기 내부에 보관하며, GitHub 업데이트 확인·다운로드에만 인터넷을 사용합니다. Android 12 이상을 지원합니다.

## 기능

- 시작 전 몸무게·혈압, 종료 후 초기배액량·기계 제수량 입력과 총 제수량 자동 계산
- 새 기록은 측정값·사용 구성을 빈 상태로 시작, 구성 이름·대표 색상, 과거 날짜 입력, 초안 보관
- 추가투석은 물품 사용만으로 저장하며 배액량 또는 배액무게를 선택 기록
- 품목 색상, EA 재고, 날짜별 일괄 입고, 사용·입고 취소, 현재 재고 확인, 사유별 수량 추가·차감과 조정 취소
- 오늘·어제 미작성 안내와 완료 표현, 기록 목록·달력·확대 가능한 전체화면 표, 기간별 라인차트·항목별 도표·공통 기간 선택기
- JSON 내보내기·전체 복원, 선택 폴더에 자동 백업, 선택형 앱 잠금·기기 알림

## 개발 및 빌드

JDK 17, Android SDK 36, Build Tools 36, Gradle Wrapper 8.13을 사용합니다. Android Studio에서 이 폴더를 열거나 아래 명령을 실행합니다. SDK 위치는 `local.properties` 또는 `ANDROID_HOME`으로 설정합니다.

```sh
./scripts/build.sh :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
```

개발용 APK: `app/build/outputs/apk/debug/app-debug.apk` (`com.poyal.perilog.debug`).

처음 앱을 배포할 때만 서명 키를 생성합니다. 이미 배포한 앱을 다른 컴퓨터에서 빌드할 때는 기존 `.signing/` 폴더와 `signing.properties`를 프로젝트 루트에 복원하고 `assembleRelease`만 실행합니다. `.signing/`은 숨김 폴더입니다. SDK와 JDK 경로는 해당 컴퓨터에 맞춰 설정합니다.

```sh
./scripts/create-signing.sh
./scripts/build.sh :app:assembleRelease
```

설치용 APK: `app/build/outputs/apk/release/app-release.apk` (`com.poyal.perilog`). `.signing/`과 `signing.properties`는 버전 관리에서 제외합니다. **두 항목을 별도로 안전하게 보관하고 앱 업데이트에 같은 키를 사용해야 합니다.** 기존 키를 덮어쓰지 않습니다.

v1.0.8의 버전 코드는 9이며, 직전 공개 v1.0.7의 버전 코드는 8입니다. 기존 앱과 같은 키로 서명한 APK를 배포합니다. 서명 키와 원본 백업 ZIP은 `.signing/`에 로컬 보관하며 Git과 공개 첨부 파일에서는 제외합니다. Room 스키마 1→2→3→4→5→6→7→8 이전 검사가 기존 기록·사용 내역·초안·구성·입고·실사·설정을 확인합니다. 스키마 5에서는 연락처 이모지·전화/문자 허용과 예약의 치료 항목 목록을 추가하고, 기존 치료 구성 안의 항목은 개별 등록 항목으로 이전합니다. 스키마 6은 예약에 진료과 ID별 시간 목록을 추가하며, 이전 공통 시간과 진료과 스냅샷을 그대로 보존합니다. 스키마 7에서는 수량 추가·차감 이력 테이블을 추가합니다.

에뮬레이터나 개발용 Android 기기가 연결된 경우:

```sh
./scripts/build.sh :app:connectedDebugAndroidTest
```

일반·큰 글씨·오프라인 E2E 반복 실행은 [E2E 테스트 안내](E2E-테스트.md)를 참고하세요.

GitHub Actions의 반복 실패와 긴 대기를 줄이기 위해 Android 검증 워크플로는 수동 진단으로만 실행합니다. 개발 중에는 관련 로컬 검사부터 수행하고, 확정한 릴리즈 후보의 전체 로컬 검증을 한 번 마치면 그 APK를 그대로 게시합니다. main·PR 푸시마다 전체 원격 검사를 실행하거나 원격 통과를 기다리지 않습니다.

UI 테스트는 개발용 패키지 데이터를 테스트 자료로 교체하므로 본인의 실제 기록은 출시용 패키지를 사용하세요.

## 구현 구조

- `data`: Room 엔티티·DAO·트랜잭션·감사 이력·버전 1 JSON 모델
- `domain`: 제수량 계산, 완료 조건, 신규 기록 초기화, 재고 배정·실사 기준, 가져오기 검증
- `ui`: Compose 화면·입력 보조·ViewModel 상태
- `backup`: 파일 검증·복원 보호 백업·WorkManager·로컬 알림
- `widget`: Glance 기록·병원 일정 위젯, 실제 크기별 배치·데이터·갱신·이동. [위젯 개발 가이드](위젯-개발-가이드.md)를 참고하세요.

재고는 저장된 입고·사용·실사·조정 이벤트로 계산합니다. 치료 ID와 사용 ID를 연결해 재저장 시 중복 차감을 막습니다. 기록 삭제는 연결된 사용 취소를 같은 트랜잭션에서 수행하고, 되돌리기는 삭제 전 기록·사용 상태를 복원합니다. 이미 취소된 사용은 다시 활성화하지 않습니다. `adjustments`는 부호가 있는 수량과 필수 사유·날짜·취소 상태를 보관하며 재고 실사 기준을 새로 만들지 않습니다. 재저장·취소는 같은 ID를 사용하고 전체 백업·복원에도 포함합니다. Room 스키마 6→7은 기존 자료를 보존하며 빈 조정 테이블을 추가합니다. 사용기한 입력·표시·안내는 제거했고 재고는 입고 순서로 차감합니다. 예전 JSON의 `expiry`·`expiryDays`는 호환성을 위해 보존하지만 재고 계산·화면에는 사용하지 않습니다. 설정 복원도 치료·재고와 같은 트랜잭션으로 처리하기 위해 사용자 설정은 Room에 저장하고, 폴더 접근 권한과 백업 실행 상태는 DataStore에 별도로 보관합니다.

Room 스키마는 `app/schemas/`에서 관리합니다. 후속 DB 버전에는 명시적인 마이그레이션과 테스트를 추가해야 하며 파괴적 초기화는 허용하지 않습니다.

현재 Room 스키마는 8입니다. 7→8은 `ReplenishmentPlan` 테이블과 입고의 nullable `requestPlanId`를 추가하고 기존 자료를 보존합니다. JSON의 `replenishmentPlans`는 생략하면 빈 목록으로 읽어 이전 백업과 호환됩니다. 저장한 요청에는 입력 조건, 사용 구성 사본, 계산 당시 재고·당일 사용·참고 기간의 일평균 사용량과 최종 요청량을 보관합니다. 저장 후 과거 기록이나 재고가 달라져도 요청이 자동으로 바뀌지 않으며, 사용자가 새 계산을 비교해 적용합니다. 연결 입고가 생기면 기준을 고정합니다. 실제 재고는 기존 `Receipt`만 반영하고 요청 자체는 반영하지 않습니다.

`domain/Replenishment.kt`는 확정 사용일 평균·주간 구성 비율·직접 사용량과 날짜별 변경을 계산합니다. `SupplyAmount`는 유리수로 중간값을 유지하며 최종 요청 EA만 올림합니다. 오늘 확정된 사용의 중복 차감, 미등록 재고와 0, 방문 전 부족과 요청량을 구분합니다. 연결된 입고의 수정·취소와 초과 입고는 `requestProgress`에 반영됩니다.

사용 안내는 `ui/GuideContent.kt`의 목차·단계와 `assets/guide`의 실제 촬영 PNG로 구성합니다. `GuideScreens.kt`는 검색·오프라인 열람·이미지 확대를 제공하고, 화면 제목의 ?는 `guideForRoute`로 연결합니다. 기존 입력 화면은 `SaveableStateProvider`에 남아 도움말에서 돌아오면 입력과 스크롤을 복원합니다.

통합 재고 이력은 입고·사용·조정·실사에서 읽기 모델을 만들며 원본 이벤트나 재고 수량을 변경하지 않습니다. 입고의 같은 품목 줄은 합산하고, 품목 필터는 ID로 구분합니다. 취소 상태와 날짜·종류·품목 조건을 함께 적용하며, 실사는 증감량 대신 새 기준 수량을 표시합니다. 취소·수정은 기존 Repository 트랜잭션으로 처리하고 연결된 투석 기록이 없으면 기록 보기 버튼을 표시하지 않습니다.

진료과별 예약시간은 각 예약의 `departmentTimes`에 저장합니다. 등록된 진료과 자체에 시간을 저장하지 않으므로 다른 날짜의 예약과 독립적입니다. 이전 예약·백업에 목록이 없으면 해당 예약의 공통 `time`을 사용합니다. 홈 정렬은 현재 시각 이후에 남은 진료 중 가장 빠른 시간을 기준으로 하며, 마지막 진료시간이 지나야 지난 일정으로 분류합니다. 다음 예약 재사용은 진료과를 유지하고 모든 시간을 비웁니다.

진료과·치료 항목·예약·연락처는 별도 Room 테이블과 Snapshot 목록으로 관리합니다. 예약에는 선택 당시 진료과 이름·색상과 복수로 선택한 치료 항목 이름·아이콘을 보관해 원본 삭제·수정 후에도 내용을 유지합니다. 이전 예약의 치료 구성과 이전 JSON 백업도 읽을 수 있으며, 기존 구성의 각 항목은 안정적인 ID로 분리해 사용합니다. 예약 관리 데이터는 물품 사용·재고 계산에 영향을 주지 않습니다. 시간 판정은 기기 현지 시각을 사용하며 30초 주기와 앱 복귀 시 갱신합니다. 연락처는 이모지와 전화·문자 허용을 각각 저장하고, 홈의 연결 방법 모달에는 허용한 방법만 표시합니다. 전화·문자는 ACTION_DIAL·ACTION_SENDTO Intent로 작성 화면만 열고 직접 실행 권한을 요청하지 않습니다.

설계 이력은 [plan.md](plan.md), 설치·사용 방법은 [사용 안내](사용-안내.md), 검증 결과와 기기 확인 항목은 [검증 기록](검증-기록.md)을 참고하세요.

## 주요 기준

- 기계 총 제수량 = 초기배액량 − 이전 최종 주입 **설정값** + 기계 제수량. 설정 기본값은 2000mL이며 과거 기록에는 당시 기준을 보존합니다.
- 배액무게(g/kg)는 부피(mL)로 환산하지 않습니다. 기계투석과 손투석의 결과를 임의 합산하지 않습니다.
- 백업은 암호 없는 JSON입니다. 복원은 합치기가 아닌 전체 교체이며 사전에 현재 데이터를 보호 백업합니다.
- OS 클라우드 백업을 사용하지 않습니다. 인터넷 권한은 GitHub 업데이트 확인·다운로드에만 사용합니다. 사용자가 파일 선택기에서 선택한 저장 위치의 동작은 해당 파일 제공자에 따릅니다.

구현 시 참고한 공식 문서: [Android 빌드 도구](https://developer.android.com/build/releases/gradle-plugin), [Room](https://developer.android.com/jetpack/androidx/releases/room), [Compose 버전 조합](https://developer.android.com/develop/ui/compose/bom/bom-mapping).

## 문서용 실행 화면 촬영

루트 [README](../README.md)는 사용자 매뉴얼입니다. 작성·수정할 때는 [README 작성 가이드](README-작성-가이드.md)를 먼저 읽고 따릅니다. 개발·계획·검증 문서는 이 `docs/` 폴더에 보관합니다. `design/`은 초기 디자인 시안이며, 실제 앱 캡처와 구분합니다.

**초기화해도 되는 촬영 전용 Android 에뮬레이터**를 실행한 뒤 다음 명령으로 문서 화면을 촬영합니다. 예시 serial은 해당 에뮬레이터의 값으로 바꿉니다. 사용자가 수동 테스트 중인 에뮬레이터에는 실행하지 않습니다.

```sh
PERILOG_SERIAL=emulator-5554 ./scripts/capture-screenshots.sh
```

`docs/capture/DocumentationCapture.kt`는 `-PcaptureScreenshots`가 있을 때만 Android 테스트에 추가됩니다. 촬영 전에 선택한 에뮬레이터의 개발용 앱 데이터를 초기화하고 예시 자료를 넣은 뒤 실제 화면을 PNG로 저장합니다. 출시용 패키지는 변경하지 않습니다. 개인 기기의 실제 기록에는 사용하지 않습니다. 결과는 `docs/screenshots/`에 저장합니다. 실제 촬영 목록은 캡처 코드와 생성된 PNG를 확인하며, 별도로 수동 촬영한 화면도 함께 점검합니다. 촬영 날짜에 따라 예시 날짜도 달라집니다. 사용한 앱·OS·촬영 조건은 [화면 안내](화면-안내.md)에 기록합니다.

입고 요청과 안내 화면은 `docs/capture/ReplenishmentCapture.kt`에서 추가 촬영합니다. 앱 구현 → 실제 화면 촬영·검토 → 안내 작성 → 이미지 번들 → 안내 자체 촬영 순서로 갱신합니다. 이미지 수집만 필요하면 `python scripts/collect-guide-screens.py <serial> --avd <촬영용 AVD 이름>`을 사용합니다. `python scripts/sync-guide-assets.py`는 안내에서 참조한 실제 PNG를 앱에 복사하고, `--check`는 문서와 앱 이미지의 바이트 일치를 검사합니다. 안내 이미지를 바꾸면 APK를 다시 빌드해야 합니다.

## GitHub 릴리즈 게시

릴리즈 준비·게시·중단 후 재개 때마다 **[페리로그 전용 로컬 검증 후 배포 운영 가이드](로컬-검증-후-배포-운영-가이드.md)를 먼저 읽고 따릅니다.** [검증 기록 템플릿](releases/릴리즈-검증-템플릿.md)으로 해당 실행의 결과와 근거를 남깁니다.

로컬에서 검증한 서명 APK를 그대로 배포합니다. `.github/workflows/release.yml`은 태그의 APK·체크섬·스크린샷 ZIP을 업로드하고 공개하며 재빌드하지 않습니다. 서명 키를 Actions에 전달하지 않습니다. 현재 워크플로는 검사 결과·서명·업데이트 데이터 보존을 자동 확인하지 않으므로 **태그 푸시 전에** 운영 가이드의 필수 검사를 모두 확인합니다.

릴리즈 태그는 최종 main 소스·문서 커밋의 바로 다음에 `.release/`의 해당 버전 세 파일만 추가한 별도 커밋을 가리킵니다. 그 배포 커밋은 main에 합치지 않습니다. 빌드한 커밋·최종 소스 커밋·배포 커밋의 허용 차이는 운영 가이드에서 정합니다.

`vVERSION` 태그 푸시와 `release/vVERSION` 브랜치 푸시는 모두 실제 게시를 시작합니다. 중복으로 실행하지 않습니다. 기존 태그가 있지만 실행이 없는 경우에만 상태를 확인하고 수동 게시 경로를 사용합니다.

기존 릴리즈·태그·다른 바이트의 동명 파일을 덮어쓰지 않습니다. `scripts/publish-release.py`는 기존 초안과 공개 파일을 조회·검증하고 동일한 파일은 보존하며 누락 파일만 업로드합니다. 업로드 후 세 파일을 다시 내려받아 원본과 GitHub SHA-256을 확인한 뒤 공개합니다. 공개 파일 세 개를 다시 내려받아 원본과 서명을 확인한 뒤 게시 완료로 기록합니다.

## 업데이트 기능 검사

`./scripts/test-updates.sh`는 전용 에뮬레이터에서 작은 개발 서명 APK를 로컬 루프백 HTTP 서버로 제공해 DownloadManager, 체크섬 검증, 설치 화면과 취소 후 파일 보존을 확인합니다. GitHub 네트워크를 사용하지 않습니다. 실행 APK를 실제 설치하지 않고 설치 화면에서 취소합니다. 출시 키는 사용하지 않으며 `.tools/update-fixture/`에 검사 파일을 만듭니다.

일반 UI 검사는 `PerilogTestRunner`가 GitHub 응답을 대체하므로 실제 공개 버전과 무관합니다. 디버그 빌드만 루프백 HTTP를 허용하며 출시 빌드는 HTTPS를 사용합니다. 업데이트 메타데이터는 기기 DataStore의 `appUpdate` 키에 저장하고 기록 DB와 백업 JSON에는 추가하지 않습니다.
