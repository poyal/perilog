# 페리로그 로컬 검증 후 배포 운영 가이드

적용 대상: `poyal/perilog`의 Android APK 직접 배포. 작성일: 2026-10-02. 다음 릴리즈부터 매번 이 문서를 먼저 읽고 검사·기록·게시 순서로 진행한다. 현재 도구와 과거 검증 수치는 작성일 기준이며, 실제 배포 시 저장소와 GitHub 상태를 다시 확인한다.

**목적은 GitHub Actions의 반복 실패와 긴 설치·빌드·에뮬레이터 대기를 줄이는 것이다.** 검사 수나 문서 절차를 늘리는 것 자체가 목적이 아니다. 개발 중에는 관련 로컬 검사만, 릴리즈 후보가 확정되면 전체 로컬 검사를 한 번 수행한다. Actions는 검증된 파일의 게시 또는 필요한 경우의 수동 환경 진단만 담당한다.

페리로그는 로컬에서 서명한 APK를 GitHub Actions가 **재빌드 없이 그대로 게시**한다. 이 구조를 유지한다. 데스크톱용 Node·Electron·DMG·NSIS 명령이나 다른 프로젝트의 검사 결과를 사용하지 않는다.

## 1. 현재 구현과 운영 규칙

| 구분 | 현재 동작 |
| --- | --- |
| 빌드·단위·Lint | `scripts/build.sh`와 Gradle 작업 |
| 기본/큰 글씨 UI 검사 | `scripts/test-e2e.sh all` |
| 실제 프로세스 종료 후 복구 | `scripts/test-process-restore.py` |
| 원격 진단 | `.github/workflows/test.yml`: `workflow_dispatch`로 요청한 경우에만 검사. main·PR 자동 실행 없음 |
| 릴리즈 게시 | `.github/workflows/release.yml`: 태그의 세 파일 검사, 초안 생성·누락 파일 업로드·재다운로드/해시 검증 후 공개 |
| 게시 동시 실행 제어 | Actions의 `android-release-publish` concurrency 그룹 |
| 아직 없는 기능 | 통합 `release:verify`/`release:publish`, 검증 기록을 강제 검사하는 게시 코드, 작업 폴더 간 잠금 |

이 문서는 **작업자가 지켜야 하는 필수 절차**다. 문서를 추가했다고 자동 차단 기능까지 구현된 것은 아니다. 현재 게시 워크플로는 단위·UI·업데이트 검증 결과나 APK 서명을 확인하지 않는다. `scripts/publish-release.py`는 세 파일의 체크섬·GitHub 자산 해시·재다운로드 바이트를 확인한 뒤 공개하며, 재실행 시 동일 파일은 보존하고 누락 파일만 업로드한다. 따라서 태그 푸시 전 필수 결과를 직접 확인하고 게시 후 공개 파일을 재검증한다. 검증 기록이 없으면 게시하지 않는다.

무거운 원격 검사를 릴리즈 대기 조건으로 두지 않는다. 동일한 로컬 검사가 통과한 뒤 확인 목적만으로 전체 원격 검사를 다시 돌리지 않는다. 수동 진단은 러너 환경 차이처럼 로컬로 해소할 수 없는 특정 문제가 있을 때만 실행하고, 발견한 문제는 가능한 한 로컬 회귀 검사로 남긴다.

| 작업 단계 | 실행 범위 | 피할 반복 |
| --- | --- | --- |
| 개발 중 수정 | 변경 관련 단위 검사·실패 재현 시나리오 | 수정/커밋마다 전체 E2E·릴리즈 패키징 |
| 후보 확정 | 아래 필수 로컬 검사를 한 번, 결과와 APK 고정 | 같은 소스를 CI에서 다시 빌드·검사 |
| 게시 | 체크섬 확인·기존 APK 업로드·공개 파일 검증 | SDK 설치·에뮬레이터 부팅·재빌드 |
| 원인 조사 | 먼저 로컬 집중 검사, 필요할 때만 수동 Actions | 원인 확인 없이 Actions 재실행 반복 |

실행 기록에는 전체 로컬 검증과 게시 소요 시간을 남긴다. 정상 운영에서 main·PR 푸시만으로 Android 검증 Actions가 생성되지 않는지 확인한다. 이미 실행·대기 중인 작업은 트리거 변경으로 자동 취소되지 않으므로 전환 시 따로 확인한다.

## 2. 릴리즈 시작 전 확정할 것

1. `git status`, 현재 브랜치, 원격 `main`, 최신 공개 릴리즈와 태그를 확인한다. 다른 컴퓨터에서 올린 변경을 가져오고 사용자 미커밋 변경을 덮어쓰지 않는다.
2. 배포할 `versionName`, 증가한 `versionCode`, 릴리즈 노트, 변경 범위를 확정한다. 기존 공개 버전·태그·APK를 덮어쓰지 않는다.
3. 해당 버전의 담당 작업 폴더와 게시 담당자/세션을 하나로 정한다. 다른 컴퓨터·체크아웃·수동 GitHub 조작에서 같은 버전을 동시에 게시하지 않는다.
4. [검증 기록 템플릿](releases/릴리즈-검증-템플릿.md)을 실행별 기록으로 복사하고 모두 `미실행`에서 시작한다. 이전 기록의 성공 표시를 복사하지 않는다.
5. 실패 자료를 덮지 않도록 `.tools/release-checks/<실행 ID>/`를 새로 만든다. 실행 ID에는 UTC 시각·버전·커밋을 포함한다. 로그를 만들 수 없거나 경로가 충돌하면 실행 전에 경로를 바로잡는다.

Actions concurrency는 그 워크플로의 작업끼리만 제어한다. 로컬 빌드나 다른 컴퓨터의 수동 업로드를 잠그지 않는다. 현재 로컬 잠금은 미구현이므로, 진행 중인 작업을 확인하고 한 작업 폴더에서 Gradle·ADB 검사·게시 작업을 겹쳐 실행하지 않는다. 향후 잠금을 구현하면 같은 저장소의 여러 worktree와 여러 컴퓨터에서 무엇을 막는지 별도로 검증한다.

## 3. 도구와 서명 준비

현재 기준은 JDK 17, Gradle Wrapper 8.13, Android SDK/Build Tools 36, 최소 Android API 31이다. 실제 Gradle 설정과 도구 버전을 확인해 기록한다. 데스크톱 OS마다 APK를 따로 만들 필요는 없으며 Android 실행 환경에서 검사한다.

`scripts/build.sh`는 `.tools/jdk`, `.tools/android-sdk`, `.tools/gradle-home`이 있으면 우선 사용한다. 새 컴퓨터에서는 JDK·SDK 위치를 `JAVA_HOME`, `ANDROID_HOME` 또는 `local.properties`에 맞춘다. 준비된 도구가 없는 worktree에서는 다른 작업 폴더의 산출물을 실수로 쓰지 않도록 경로를 명시한다.

- 기존 `.signing/`과 `signing.properties`를 프로젝트 루트에 복원한다. 키가 없다고 새 키를 생성하지 않는다. `create-signing.sh`는 최초 배포용 키 생성에만 사용한다.
- 키·비밀번호는 로그에 출력하지 않는다. 키 백업은 별도 개인 파일로 취급하고 `.release/`, 스크린샷 ZIP, Git, 공개 릴리즈에 넣지 않는다.
- `assembleRelease` 성공만으로 서명 완료를 판단하지 않는다. 현재 Gradle은 `signing.properties`가 없으면 서명 없는 릴리즈도 만들 수 있다.
- 직전 공개 APK와 후보 APK를 `apksigner verify --verbose --print-certs`로 확인한다. 앱 ID는 `com.poyal.perilog`, 개발용은 `.debug` 접미사이며, 출시 APK에 개발용 ID가 들어가면 중단한다.
- 인증서 SHA-256은 직전 공개 APK와 같아야 한다. 작성일의 공개 인증서 지문은 `79adbeead4f7fbc2a5bf99219ee2fdd909f14eb18817c2b4f6139edbce0937dd`다. 향후 키 변경은 별도 호환성 설계와 검증 없이 진행하지 않는다.

의존성 버전과 저장소 설정을 확인하고 깨끗한 후보 작업 폴더에서 빌드한다. 현재 Gradle 의존성 잠금 파일은 없으므로 잠금 파일로 전체 의존성을 재현했다고 기록하지 않는다. `clean`은 프로젝트 빌드 산출물을 지우는 작업이며 의존성 캐시 전체를 초기화하는 작업은 아니다. 의존성이 바뀌면 그 버전과 해석 결과를 별도 기록한다.

## 4. 커밋 확정과 검증 범위

앱 코드·빌드 설정·검사 코드를 먼저 커밋하고 깨끗한 작업 트리에서 배포 후보를 빌드한다. 검증 도중 이 파일들이 바뀌면 이전 APK와 결과를 새 소스의 결과로 취급하지 않는다.

| 검사 | 실행 범위·적용 조건 | 통과 조건 |
| --- | --- | --- |
| 단위·저장소 | 해당 소스의 전체 테스트, Room API 31·35 검사 포함 | 예상 테스트가 모두 실행되고 실패·오류·생략 0 |
| 정적 검사 | `lintDebug` 및 릴리즈 빌드의 필수 Lint | 오류 0, 남은 경고 내용 기록 |
| 전체 UI | API 35에서 기본 글씨와 1.5배 글씨 각각 전체 `AppFlowTest` | 두 프로필 모두 예상 테스트 전체 실행, 실패·생략 0 |
| 키보드 추가 회귀 | UI·Activity·입력·SDK/Compose를 변경한 후보는 API 36 기본/큰 글씨 검사 추가 | 입력값·입력칸·저장 버튼·하단 탭 동작 확인. 무관한 변경은 제외 이유 기록 |
| 프로세스 복구 | API 35에서 실제 PID 종료 후 미저장 폼 복구 | 이전 PID 종료, 새 PID, 값 복구·버리기 확인 |
| 신규 설치 | 비어 있는 검증용 에뮬레이터에 최종 서명 APK 설치 | 설치·실행·기록 저장·재고·설정 진입 성공 |
| 업데이트 | 직전 공개 APK → 최종 후보 APK, 삭제 없이 설치 | 5절의 데이터·권한·백업 비교 통과 |
| 산출물 | APK, 스크린샷 ZIP, 체크섬 | 버전·앱 ID·서명·파일 해시·ZIP 내용 확인 |
| 원격 진단 | 일반 릴리즈에는 불필요. 원격 환경 문제를 조사할 때만 실행 | 실행했다면 원인·커밋·결과 기록. 미실행을 배포 실패로 취급하지 않음 |

APK와 실행 환경의 API/ABI를 구분해 기록한다. API 31 Robolectric 검사는 Android 12 실제 설치 검사를 대신하지 않는다. 최소 SDK·OS 호환 동작을 변경하면 API 31 실제 설치·실행 검사도 추가한다. Galaxy Z 플립7 실물의 접기·펼치기, 삼성 키보드·파일 선택기·생체 인증·장시간 절전 동작은 수행 여부를 따로 적으며 에뮬레이터 통과로 대체하지 않는다.

필수 검사에서 실패·시간 초과·검사 실행의 예기치 않은 강제 중단·예상 테스트 누락·필수 검사 생략은 모두 배포 보류다. 프로세스 복구 검사가 의도적으로 종료하는 시험 앱의 PID는 이 중단과 구분한다. 보고서 파일이 없거나 테스트가 0개면 성공으로 기록하지 않는다. 테스트 이름 목록을 소스와 대조하고, 이전 버전보다 개수가 줄었다면 이유를 확인한다. 현재 29개 단위/저장소·프로필별 15개 UI라는 숫자는 과거 기준이지 앞으로의 고정 통과 기준이 아니다.

API 36의 지정 회귀처럼 처음부터 범위를 제한한 검사는 그 범위의 결과로만 기록한다. 실패한 전체 검사 대신 일부 검사만 실행해 전체 통과로 바꾸지 않는다. 재실행해서 우연히 통과한 경우 원인과 재현 조건을 해결하기 전에는 통과 처리하지 않는다. 기능 변경이 없는 문서 수정 때문에 앱 검사를 반복하지는 않되, 아래 커밋 차이 검사를 통과해야 한다.

전체 검증 중 실패하면 관련 시나리오로 원인을 수정·확인한 뒤 수정한 후보에 필요한 검사를 수행한다. 코드 수정 없이 같은 APK로 게시를 재개하는 경우 빌드·전체 E2E를 반복하지 않고 기존 검증 기록과 파일 해시를 재확인한다. 필수 검사를 생략해서 시간을 줄이는 대신 개발 중 전체 검사의 빈도와 로컬/원격 중복을 줄인다.

### 현재 제공되는 실행 명령

명령은 페리로그 프로젝트 루트에서 실행한다. 예시 serial은 검사 전용 에뮬레이터로 바꾼다. 개인 기기와 수동 테스트용 자료가 든 에뮬레이터를 대상으로 삼지 않는다. 각 명령의 종료 코드와 전체 로그를 실행별 폴더에 보관한다.

```sh
./scripts/build.sh clean :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleRelease

# API 35 전용 에뮬레이터. 단일 검사 환경변수가 남아 있지 않게 한다.
env -u PERILOG_TEST_TARGET \
  PERILOG_SERIAL=emulator-5554 \
  PERILOG_RESULTS_DIR="$PWD/.tools/release-checks/실행ID/api35" \
  ./scripts/test-e2e.sh all

PERILOG_SERIAL=emulator-5554 ./scripts/test-process-restore.py

# UI·Activity·입력·SDK/Compose 변경 시 API 36 추가 회귀를 확인한다.
PERILOG_SERIAL=emulator-5556 \
  PERILOG_TEST_TARGET='com.poyal.perilog.AppFlowTest#typedDraftSurvivesActivityRecreationRotationAndDoesNotConsumeStock' \
  PERILOG_RESULTS_DIR="$PWD/.tools/release-checks/실행ID/api36-keyboard" \
  ./scripts/test-e2e.sh all
```

`실행ID`는 새로 만든 실제 실행 폴더 이름으로 바꾼다. `test-process-restore.py`의 출력은 현재 `.tools/e2e-results/process/`에 고정되어 있으므로 다음 실행 전에 실행별 폴더로 복사한다. 단위·Lint 결과도 다음 Gradle 실행에 덮일 수 있으므로 보관 후 해시를 남긴다. `.tools/` 아래의 일회성 스크립트는 새 체크아웃에 없는 로컬 자료이며 공식 공통 명령으로 가정하지 않는다.

## 5. 업데이트 데이터 보존 — 매 릴리즈 필수

DB 스키마가 바뀌지 않아도 최종 서명 APK로 검사한다. 디버그 APK 위에 디버그 APK를 설치한 결과나 새 설치만 성공한 결과로 대체하지 않는다.

1. 직전 공개 APK를 내려받고 공개 체크섬·서명을 확인한다. 검증용 에뮬레이터에 그 APK를 설치한다.
2. 구버전의 UI 또는 실제 백업 가져오기로 가상 데이터를 채운다. `products`, `templates`, `treatments`, `usages`, `receipts`, `counts`, `audit`, `drafts`, `settings`의 **9개 테이블에 모두 데이터가 있어야 한다**.
3. 기계·추가투석, 음수·0·미입력, mL·g·kg, 과거 계산 기준, 취소 이력, 삭제한 기록의 사용 내역, 비활성 품목, 미저장·수정 중 초안, 기본값이 아닌 설정을 포함한다.
4. 구버전에서 실제 파일 선택기로 자동 백업 폴더를 연결하고 백업을 만든다. 재고 화면 수량, 전체 내보내기 JSON, DB 행과 필드, 앱 내부 보호 백업, DataStore, 알림·폴더 권한을 보관한다.
5. 앱을 삭제하거나 데이터를 지우지 않고 `adb -s <검증용 serial> install -r <최종 후보 APK>`로 덮어 설치한다. 실제 앱을 실행해 DB 이전이 일어나도록 한다. 앱 UID와 최초 설치 시각이 유지되는지도 확인한다.
6. 전후 데이터는 행 수뿐 아니라 ID와 **기존 필드 값 전체**를 비교한다. 신규 컬럼은 계획한 기본값을 확인한다. 의도한 변환이 있다면 필드별 변환 규칙과 예상 결과를 미리 기록한다. 알 수 없는 손실·재고 변화·초안 소실은 실패다.
7. 업그레이드된 앱의 재고 화면과 내보내기 JSON을 비교한다. 기존 백업이 남아 있고 폴더를 다시 연결하지 않아도 새 백업이 만들어지는지 확인한다. 정상 동작으로 바뀌는 백업 시각 등과 보존해야 하는 값을 구분한다.

v1.0.4부터 업데이트 메타데이터가 기기 DataStore에 추가되므로 파일 전체 해시가 달라질 수 있다. 기존 백업 폴더·백업 상태 등 기존 키의 값 보존과 새 `appUpdate` 키만 추가됐는지 비교한다.

DB 사본은 앱을 멈춘 상태에서 WAL을 함께 수집하거나 일관된 스냅샷으로 읽는다. root가 가능한 **검증용 에뮬레이터**만 DB 직접 비교에 사용한다. 앱/키/도구 설치·교체 기록과 검사 스크립트를 해당 실행 자료에 남긴다.

DB 마이그레이션 경로를 변경하면 지원하는 이전 스키마의 단위 검사도 모두 실행한다. 이전 버전으로 APK를 다시 설치하는 것은 DB 되돌리기가 아니므로 장애 대응으로 제안하지 않는다. 공개 후 결함은 새 versionCode의 수정 릴리즈와 검증된 복구 절차로 처리한다.

2026-10-02의 v1.0.2→v1.0.3 검사는 공개 APK 두 개로 9개 테이블·48행·500개 기존 필드 값, 재고 표시와 백업·권한 보존을 확인했다. [검증 기록](검증-기록.md)에 결과를 남긴다. 이 결과는 다음 릴리즈의 검사를 대신하지 않는다.

업데이트 기능을 변경했다면 `./scripts/test-updates.sh`로 다운로드·설치 연결·공용 파일 보존을 로컬 검사한다. 게시 스크립트 변경 시 `python3 -m unittest discover -s scripts/tests -v`와 actionlint를 실행한다.

## 6. 검증한 APK 고정과 문서 마무리

서명 빌드가 끝난 APK를 `dist/perilog-VERSION.apk`에 복사하고 크기·SHA-256을 기록한다. 이후 신규 설치·업데이트 검사는 이 파일을 사용한다. 검증 후 APK를 다시 만들거나 교체했다면 새 해시의 후보로 보고 APK 의존 검사를 다시 수행한다.

해당 UI에 맞게 README·사용 안내·릴리즈 노트·스크린샷을 갱신한다. README는 먼저 [README 작성 가이드](README-작성-가이드.md)를 읽고 사용자 매뉴얼로 유지하며, 버전별 변경 요약은 릴리즈 노트에 남긴다. 스크린샷 ZIP에는 현재 매뉴얼이 사용하는 번호 붙은 PNG만 넣고 이름·개수·원본 일치·압축 무결성을 확인한다. 파일 이름이나 과거의 24장이라는 숫자만 보고 이번 화면이라고 판단하지 않는다.

최종 배포 파일은 다음 세 개다.

```text
perilog-VERSION.apk
perilog-VERSION-screenshots.zip
perilog-VERSION.sha256
```

체크섬 파일에는 APK와 스크린샷 ZIP의 SHA-256 및 파일 이름을 각각 한 줄씩 기록한다. 정확히 두 항목이며 누락·중복·다른 파일 경로가 없어야 한다. 문서와 공개 릴리즈 노트에는 비밀번호·키 경로의 내용·개인 자료를 넣지 않는다.

## 7. 빌드 커밋·최종 소스 커밋·태그의 관계

페리로그의 릴리즈 태그는 `.release/` 파일만 추가한 배포 커밋을 가리킨다. 다른 프로젝트처럼 검증 커밋과 태그 커밋이 무조건 같다고 검사하면 안 된다.

| 기록 항목 | 의미 | 허용하는 차이 |
| --- | --- | --- |
| `buildCommit` | 깨끗한 트리에서 APK를 빌드하고 검사를 실행한 커밋 | 빌드·검사 출처 |
| `sourceCommit` | 검증 결과와 화면을 반영한 최종 main 커밋 | `buildCommit` 이후 사용자 문서·릴리즈 노트·검증 요약·번호 붙은 화면 PNG만 변경 가능 |
| `releaseCommit` | `sourceCommit`의 바로 다음 배포 커밋 | `.release/`의 해당 버전 세 파일 추가만 허용 |
| `tag` | `vVERSION` | annotated tag를 해석한 커밋이 `releaseCommit`과 동일 |

기본은 `buildCommit == sourceCommit`이다. 검증 뒤 문서·캡처를 반영했다면 정확한 변경 파일 목록을 기록하고 허용한 내용만 있는지 확인한다. `app/`, Gradle 설정, `scripts/`, `.github/`, `docs/capture/`의 검사 코드는 문서 예외에 포함하지 않는다. 특히 `docs/` 아래라는 이유로 Kotlin 캡처 코드를 제외하면 안 된다. 운영 규칙 변경으로 필수 검사 범위가 달라졌다면 새 기준을 충족하는지도 다시 평가한다.

후보를 확인하는 명령 예시다. 변수에는 기록한 실제 커밋을 넣고, 출력 전체를 확인한다.

```sh
git diff --name-status "$PERILOG_BUILD_COMMIT" "$PERILOG_SOURCE_COMMIT"
git rev-parse "$PERILOG_RELEASE_COMMIT^"
git diff --name-status "$PERILOG_SOURCE_COMMIT" "$PERILOG_RELEASE_COMMIT"
git rev-parse "v$PERILOG_VERSION^{}"
```

`releaseCommit`은 단일 부모 커밋이어야 하며 그 부모는 `sourceCommit`이다. 마지막 차이는 정확히 `A .release/perilog-VERSION.apk`, `A .release/perilog-VERSION-screenshots.zip`, `A .release/perilog-VERSION.sha256`이어야 한다. 임의 조상 커밋, 앱 코드 변경, 다른 버전 파일을 함께 허용하지 않는다.

배포 커밋 해시는 커밋 자체에 자기 해시로 넣을 수 없다. 태그 생성 후 로컬 검증 기록에 추가하고, 게시 확인 후 main의 검증 요약에 남긴다. 그 해시를 적기 위해 이미 생성한 릴리즈 태그를 이동하지 않는다.

## 8. 게시 전 확인과 게시

1. 모든 필수 로컬 결과가 해당 후보와 일치하고 실패·미실행이 없는지 확인한다. 단위 XML·UI XML/HTML·Lint·설치/업데이트 보고서·서명 출력·파일 해시를 근거로 삼는다. 원격 CI 성공은 요구하지 않으며 과거 CI 성공으로 이번 로컬 검사를 대체하지도 않는다.
2. `docs/releases/vVERSION.md`와 다운로드 링크·스크린샷·버전 정보가 맞는지 확인한다. 검증 후 문서 전용 커밋을 추가했다면 실제 빌드/검사 커밋과의 허용 차이를 기록한다. 문서만 바뀌었다고 앱을 다시 빌드하지 않는다.
3. 깨끗한 `sourceCommit`에서 별도 `release/vVERSION` worktree를 만든다. `.release/`에 **세 배포 파일만** 복사한다. `dist/` 전체 복사는 키 백업 같은 개인 파일을 섞을 수 있으므로 금지한다.
4. 복사한 파일을 고정한 원본과 바이트 단위로 비교한 뒤 그 세 경로만 `git add -f`하고 배포 커밋·태그를 만든다. 7절의 커밋 관계와 체크섬을 다시 검사한다.
5. 동일 버전의 원격 태그·릴리즈·실행 중인 게시 작업이 없는지 확인한다. 기존 항목이 있다면 먼저 9절의 재개 절차를 적용한다.
6. `main`과 `vVERSION` 태그를 푸시한다. **태그 푸시는 실제 게시를 시작하는 동작**이다. `release/vVERSION` 브랜치 푸시도 같은 동작이므로 중복으로 푸시하지 않는다.
7. Actions 종료 상태뿐 아니라 실제 공개 릴리즈의 태그·초안 여부·버전·첨부 파일을 확인한다.
8. 공개 URL에서 APK·ZIP·체크섬을 모두 다시 다운로드한다. 세 파일이 로컬 원본과 같은지, APK 서명·앱 ID·버전이 맞는지, ZIP의 모든 파일이 이번 원본과 같은지 검증한다.
9. [검증 기록](검증-기록.md)에 실행 URL, 커밋 관계, APK/ZIP 해시, 공개 파일 비교와 남은 실기기 범위를 남긴다. 다운로드 검증이 실패했으면 게시 완료로 보고하지 않는다.

## 9. 실패·중단·재실행

| 발견한 상태 | 처리 |
| --- | --- |
| 필수 검사 실패·생략·중단 | 게시 전 중단. 원인 수정과 필요한 재검증. 실패 로그 보존 |
| 태그만 있고 게시 실행이 안 보임 | 원격 태그와 실행 목록부터 확인. 실행이 없을 때만 기존 태그를 지정해 수동 실행 |
| 초안 릴리즈가 이미 있음 | 태그·기존 파일의 해시·재다운로드 바이트를 검증하고 같은 게시 작업을 재실행. 누락 파일만 보완하며 다른 바이트는 거절 |
| 같은 이름·같은 바이트가 이미 있음 | 검증 후 보존. 파일이 있다는 이유만으로 성공 처리하지 않음 |
| 같은 이름·다른 바이트가 있음 | 덮어쓰지 않고 출처 조사. 공개 버전 수정은 새 버전으로 진행 |
| 공개됐지만 일부 파일이 없거나 내려받기 검증 실패 | 불완전 게시로 기록. 원본이 확정된 누락 파일만 복구하거나 새 수정 버전 준비. 기존 정상 설치본 삭제 금지 |

재개할 때도 게시 담당 작업은 하나로 유지한다. 기존 초안은 모든 파일을 확인한 뒤 공개한다. 현재 Actions 경로는 동일 파일의 재개와 업로드 검증을 처리하지만 서명·검증 기록 확인은 자동 처리하지 않는다. 실패 원인을 확인하고 원본이 같은 경우에만 재개한다.

## 10. Actions 운영과 전환 확인

현재 기준은 **Android 검증은 수동 진단, 릴리즈 Actions는 기존 파일 게시**다. `.github/workflows/test.yml`에서 `push`·`pull_request`를 제거하고 `workflow_dispatch`만 유지한다. `.github/workflows/release.yml`의 가벼운 게시 경로는 유지한다. 일반 릴리즈에서 원격 진단의 성공을 기다리는 `needs`나 필수 체크를 추가하지 않는다.

전환 커밋을 원격에 반영한 뒤 기본 브랜치의 실제 YAML과 실행 목록을 확인한다. 과거 커밋에는 예전 트리거가 남아 있을 수 있으므로 새 작업 브랜치와 릴리즈 후보에 전환 커밋이 포함됐는지 확인한다. PR 보호 규칙이 제거한 자동 검사 이름을 필수로 요구한다면 그 필수 체크도 운영 정책에 맞게 조정해야 한다. 권한이 없어 확인할 수 없으면 그 상태를 명시한다. 기존 실행을 성공으로 꾸미거나 검사를 빈 성공 작업으로 대체하지 않는다.

별도로 자동 게시 자체를 중단해야 하는 경우에는 게시 워크플로를 GitHub UI/CLI/API로 명시적으로 비활성화하고 이미 실행·대기 중인 게시 작업도 확인한다. `main`에서 YAML을 삭제한 것만으로 예전 커밋에 붙이는 태그의 게시까지 차단된다고 가정하지 않는다. 이번 전환은 게시 워크플로를 끄는 작업이 아니다. [GitHub 이벤트별 워크플로 선택](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows#workflow-triggers) · [워크플로 비활성화](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).

통합 검증·게시 도구를 나중에 만들면 필수 테스트 이름·실행 범위·허용 생략, 검증 기록 해시, 커밋 관계, APK 서명, 업로드 중 파일 변경, 중단 후 재개를 실제 코드에서 검사한다. 자동화가 완성되기 전까지 이 문서의 수동 확인을 생략하지 않는다.

## 11. 결과 보관

- `dist/`: 배포할 APK·스크린샷 ZIP·체크섬. 키 백업이 있어도 배포 대상으로 선택하지 않는다.
- `.tools/release-checks/<실행 ID>/`: 로컬 원본 로그·보고서·검증 데이터·스크린샷·서명/해시·설치 비교 결과. 개인 데이터·키·토큰 제외.
- `docs/검증-기록.md`: 다른 컴퓨터에서도 읽을 수 있는 실행 결과 요약과 출처.
- `docs/releases/vVERSION.md`: 사용자가 읽는 변경 내용·설치 안내·검증 범위.
- `.release/`: 별도 배포 커밋에만 들어가는 해당 버전 세 파일. main에는 합치지 않는다.

실제 사용자 DB·키·비밀번호·개인 백업·테스트 DB는 Git에 넣지 않는다. `.release/`의 검증된 공개 산출물은 페리로그가 이미 사용하는 명시적 예외다. 실패 재현 자료와 이번 배포의 근거를 다음 실행에서 덮어쓰거나 임의로 정리하지 않는다.
