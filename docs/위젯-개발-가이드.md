# 페리로그 위젯 개발 가이드

대상은 Android 12(API 31) 이상, Jetpack Glance 1.2.0을 사용하는 현재 페리로그 소스입니다. 실제 사용법은 [사용자 매뉴얼](../README.md#widgets), 실행 화면은 [화면 안내](화면-안내.md)에 있습니다. 이 문서는 구현과 검사 방법을 설명하며 디자인 시안을 실행 결과로 취급하지 않습니다.

## 1. 표시할 내용과 기본 크기

| 위젯 | 기본·조절 크기 | 내용 | 눌렀을 때 |
| --- | --- | --- | --- |
| 어제·오늘 기록 | 기본 4×2, 2×2·4×1로 조절 | 날짜별 활력 상태·사용 구성·투석 기록의 세 단계, 완료 체크와 미완료 원 | 날짜는 해당 기록·초안, 제목은 앱 홈 |
| 병원 일정 | 기본 2×2, 가로·세로 조절 | 가장 가까운 방문의 D-day·날짜·진료과별 시간·선택한 모든 처치 | 본문은 예약 수정, 제목은 일정 목록, 빈 일정은 새 예약 |

기록 위젯은 개별 측정값이나 남은 입력 항목을 표시하지 않습니다. 홈 화면과 같은 `DailyProgress` 판정을 사용하고, 추가투석만 미완료면 해당 입력으로 연결합니다. 병원 일정에는 메모를 표시하지 않습니다. 스크롤, 줄임표, `+N`으로 처치를 감추지 않는 것이 현재 제품 요구사항입니다. 앱 잠금이 켜져 있으면 내용을 가리며 앱 인증을 거쳐 이동합니다. 열기·새로고침만으로 기록을 확정하거나 재고를 차감하지 않습니다.

이동 요청은 `MainActivity`와 `JournalApp`에서 처리합니다. 위젯으로 이동하기 직전에 현재 입력 초안을 저장하고, 인증 및 날짜·예약의 존재 여부를 확인합니다. 예약이 삭제된 상태라면 목록으로 이동합니다. 화면 생명주기 재생성, 앱이 이미 열린 상태의 연속 클릭도 검사해야 합니다.

## 3. 격자 수 대신 실제 dp로 배치하기

4×2나 2×2는 홈 앱의 격자 수입니다. 같은 격자도 화면 비율·방향·홈 앱 여백에 따라 실제 크기가 다릅니다. `SizeMode.Exact`의 `LocalSize`로 받은 크기를 사용하고, `widgetViewport`에서 바깥 여백·제목·간격을 뺀 뒤 본문을 계산합니다. 고정된 2:1 비율이나 시안 이미지 높이를 가정하지 않습니다. [Android 크기 안내](https://developer.android.com/design/ui/mobile/guides/widgets/sizing), [Glance 크기 모드](https://developer.android.com/develop/ui/compose/glance/build-ui#size-mode)를 참고하세요.

기록 위젯의 현재 분기는 다음과 같습니다. 수치는 **dp**이며 격자 수가 아닙니다.

| 조건 | 배치 |
| --- | --- |
| 전체 높이 110 미만, 폭 260 이상 | `STRIP`: 좌우 날짜 카드, 각 날짜 안의 세 단계를 가로 표시(4×1) |
| 전체 높이 110 미만, 폭 260 미만 | 압축 `MATRIX`: 날짜별 두 행 |
| 폭 260 이상, 본문 높이 170 이상 | `WIDE_TALL`: 좌우 카드 안의 세 단계를 세로로 펼침 |
| 폭 260 이상, 본문 높이 170 미만 | `WIDE`: 좌우 카드 안의 세 단계를 가로 표시 |
| 폭 260 미만, 본문 높이 170 이상 | `STACKED`: 날짜 카드를 위아래로 배치 |
| 나머지 | `MATRIX`: 단계 제목과 날짜별 행 |

기록 provider는 기본 4×2를 유지하고 `minResizeHeight=48dp`, `minResizeWidth=110dp`로 한 칸 높이 조절을 허용합니다. 기본 크기의 `minHeight`만 줄이는 것으로는 조절 범위를 정확히 표현할 수 없습니다. 병원 일정의 최소 조절 크기는 110×110dp입니다. 홈 앱이 조절을 지원하는지는 별개이므로 실제 Launcher에서도 확인합니다. [유연한 위젯 레이아웃과 크기 속성](https://developer.android.com/develop/ui/views/appwidgets/layouts)을 참고하세요.

## 4. 병원 일정의 공간·텍스트 계산

`WidgetAppointmentLayout`은 진료과와 처치의 한 열·두 열 후보를 측정합니다. 넓고 낮은 공간에서는 진료과와 처치를 좌우로 나누는 후보도 고려합니다. 실제 `TextPaint`·`StaticLayout`과 같은 density·locale을 사용해 줄바꿈과 높이를 계산합니다. 렌더링에서는 목표 픽셀 크기를 sp로 역변환해 시스템 글씨 배율이 고정된 위젯 공간을 넘치게 하지 않도록 합니다. 앱 본문과 달리 위젯 글씨는 시스템 배율만큼 커지지 않으므로 더 크게 보려면 위젯 크기를 늘립니다. 먼저 간격을 줄이고 필요하면 글씨를 0.25 단위로 조절합니다.

길쭉한 공간에서는 가장 큰 글씨와 0.75dp 이내인 후보 중 줄바꿈이 적은 배치를 우선합니다. 글씨가 조금 커지더라도 처치 이름이 불필요하게 두 줄로 꺾이는 문제를 막기 위한 기준입니다. 여유 공간은 행과 구역 사이에 제한을 두고 분배하며 남은 영역을 정렬합니다. 내용 수와 길이가 무제한인 만큼 매우 작은 공간에서 읽을 수 있는 최소 글씨 크기까지 보장하지는 않습니다. 사용 안내에서도 항목이 많으면 위젯을 늘리도록 설명합니다.

측정 코드 변경 시 특히 확인할 사항:

- `TextPaint.apply` 안의 `density`와 외부 화면 density를 혼동하지 않습니다. 실제 픽셀 배율을 명시적으로 사용합니다.
- 마지막 줄의 반올림 차이를 흡수하는 2px 안전 여백을 유지합니다.
- 폭 검사는 보이지 않는 뒤쪽 공백을 포함하는 `getLineWidth` 대신 실제 보이는 범위를 나타내는 `Layout.getLineMax`를 사용합니다. 높이·잘림·줄임표 검사는 별도로 수행합니다.
- 선택한 모든 처치와 이전 백업의 치료 구성 항목까지 남아 있는지 확인합니다.
- Glance는 일반 Compose 화면이 아니라 `RemoteViews`로 변환됩니다. 직접 자식 수 제한을 피하도록 큰 목록을 묶고, 일반 Compose 전용 컴포넌트를 넣지 않습니다. [Glance UI 제약](https://developer.android.com/develop/ui/compose/glance/build-ui), [Layout.getLineMax](https://developer.android.com/reference/android/text/Layout#getLineMax(int))를 참고하세요.

## 5. 데이터·테마·갱신

위젯은 Repository의 `Snapshot`을 읽습니다. 기록 판정이나 예약 정렬을 위젯에서 별도로 재구현하지 않습니다. 시각은 기기 시간대를 따르며 오늘의 마지막 진료시간 이후에는 다음 방문으로 바뀝니다.

`WidgetUpdates`는 설치된 두 provider의 모든 인스턴스를 갱신합니다. Repository 변경과 수동 새로고침은 즉시 작업을 요청하고, WorkManager는 30분 주기 및 자정·예약 경계의 별도 작업을 예약합니다. 경계 작업은 별도의 갱신 작업을 요청해 실행 중 자신을 교체하지 않습니다. 재부팅·날짜·시각·시간대·앱 교체 방송에도 다시 요청합니다. 위젯이 없으면 주기·경계 작업을 취소합니다. `updatePeriodMillis`는 0으로 두어 중복 갱신 경로를 만들지 않습니다. WorkManager는 정확한 시각 알람이 아니므로 절전 중 지연될 수 있습니다.

라이트·다크는 앱 설정을 따르고 시스템 모드도 지원합니다. 배경·구분선·오늘 강조·완료 및 미완료 아이콘을 양쪽 테마에서 확인합니다. 시스템 위젯 모서리와 내부 패널의 여백을 유지합니다. 제목·날짜·처치·새로고침에는 의미 있는 접근성 설명을 유지합니다.

## 6. 로컬 검사와 실제 화면 확인

앱 데이터가 교체되는 UI 검사는 **초기화 가능한 전용 에뮬레이터**에서만 실행합니다. 사용자의 기록이나 수동 테스트용 에뮬레이터를 초기화하지 않습니다. Android 12(API 31), API 35, API 36에서 확인하고 API 35·36은 기본 글씨와 1.5배를 포함합니다. 전체 릴리즈 검사는 [운영 가이드](로컬-검증-후-배포-운영-가이드.md)를 따릅니다.

```sh
./scripts/build.sh :app:testDebugUnitTest --tests 'com.poyal.perilog.WidgetDataTest' --tests 'com.poyal.perilog.WidgetLayoutTest' --tests 'com.poyal.perilog.GuideTest'
PERILOG_SERIAL=emulator-5560 PERILOG_TEST_TARGET=com.poyal.perilog.WidgetFlowTest ./scripts/test-e2e.sh all
```

`test-e2e.sh`의 환경 변수·인자는 [E2E 안내](E2E-테스트.md)와 현재 스크립트를 확인합니다. Windows에서는 같은 Gradle 작업을 `gradlew.bat`로 실행하고, ADB `am instrument -w -r -e class com.poyal.perilog.WidgetFlowTest`와 테스트 runner를 이용할 수 있습니다. ADB 종료 코드만 보지 말고 예상 테스트 이름과 실제 결과·실패·누락을 대조합니다.

검사 책임은 다음과 같습니다.

- `WidgetDataTest`: 날짜·세 단계·예약 경계·잠금 등 읽기 모델.
- `WidgetLayoutTest`: 크기 경계와 배치 계산.
- `WidgetFlowTest`: 실제 `AppWidgetHostView`에서 두 테마·크기 변경·가로 화면·긴 진료과·홀수/많은 처치·이전 구성·시스템 테마·클릭·초안 보존·연락처 순서.
- `GuideTest`: 모든 화면 도움말 연결과 앱에 포함한 PNG의 원본 일치.

최소 110dp 폭, 48dp 높이의 기록, 짧은 158×172·328×172, 긴 146×274·303×274와 가로 화면을 포함합니다. 모든 날짜·단계·진료과·처치가 존재하고, 텍스트와 뷰가 부모 안에 들어가며 스크롤·줄임표가 없는지 검사합니다. 합성 호스트 검사 뒤에는 실제 Launcher에서 4×2→4×1→2×2 조절, 클릭, 밝게/어둡게, 갱신을 직접 확인합니다. 격자 크기만 검사하거나 스크린샷만 보고 통과시키지 않습니다.

## 7. 캡처·앱 안내를 함께 갱신하기

1. 변경한 구현과 관련 검사를 완료합니다.
2. `:app:assembleDebug :app:assembleDebugAndroidTest -PcaptureScreenshots`로 캡처용 APK를 만듭니다.
3. `docs/capture/WidgetDesignCapture.kt`로 실제 호스트 비교 화면을 촬영하고 Launcher의 실제 배치도 촬영합니다. 데이터는 합성 자료만 사용합니다.
4. `docs/screenshots/`의 PNG를 직접 열어 밝게/어둡게·작은/긴/한 칸 크기·구분선·아이콘·줄바꿈을 확인합니다.
5. README의 위젯 절, `docs/사용-안내.md`, `docs/화면-안내.md`, `ui/GuideContent.kt`의 `widgets` 항목과 `WidgetSettingsScreen` 안내를 맞춥니다.
6. `python scripts/sync-guide-assets.py`로 앱 이미지를 갱신하고 `--check`로 동일 바이트인지 확인합니다.
7. 앱 안내에서 검색·이미지 확대·뒤로 돌아오기까지 확인한 뒤 최종 APK를 빌드합니다. 앱 안내 이미지 변경은 문서만의 변경이 아닙니다.

현재 사용 화면은 59·63~70번이며 57·58·61번은 이전 디자인의 보관 이미지입니다. 실제 설명에 사용하는 파일만 릴리즈 화면 ZIP에 포함합니다. 이전 이미지나 시안을 새 버전 검증 근거로 재사용하지 않습니다. 개발 검사 결과는 [검증 기록](검증-기록.md), 릴리즈 후보의 실제 결과는 해당 버전 릴리즈 기록에 남깁니다.
